# The Haywire curated marketplace

A curated catalogue of [Haywire](https://github.com/going-haywire/haywire) libraries, published as three subscribable feeds.

This repo holds no library code and no packages — every package is served by
PyPI. What it holds is a **list** of which libraries are in the catalogue, and
the tooling under `scripts/` that turns that list into feeds a Haywire studio
can subscribe to.

## What subscribing gets you

Paste one of these into **Add Source** in the studio's Library Browser, or edit
`~/.haywire/db/haybale_marketplace/marketplace.toml` directly.

**stable:** versions proven to install **together**

```TEXT
https://going-haywire.github.io/marketplace/stable/marketplace.toml
```

**latest**: the newest version of each library as of the last catalogue release

```TEXT
https://going-haywire.github.io/marketplace/latest/marketplace.toml
```

**edge:** whatever is newest on PyPI right now

```TEXT
`https://going-haywire.github.io/marketplace/edge/marketplace.toml
```

`stable` is the default a fresh Haywire install subscribes to, alongside the framework's own feed at `going-haywire.github.io/haywire/marketplace.toml`.

Older catalogue releases stay available permanently: [archives](https://going-haywire.github.io/marketplace/archives.html).

### Changing channel

There is no channel switcher in the studio. Open `~/.haywire/db/haybale_marketplace/marketplace.toml` and change the `url` of
the `[[markets]]` entry. The file is created with the alternatives already
written in as comments.

**Do not subscribe to two channels at once**. They offer the same library names at different versions, and the studio will treat that as a conflict on every refresh.

### Some background

Haywire libraries install into **one shared Python environment**, one at a
time. Each install is a separate dependency resolution, so installing library B
can quietly upgrade something library A needed at an older version — and A then
fails when you next load it. Nothing in the studio can detect that.

The three channels differ in how much has been proven about the versions they
name:

- **edge** — we assert that this library is in the catalogue and that this name
  refers to this PyPI project. Nothing about the version. Regenerated nightly.
- **latest** — everything _edge_ asserts, plus: this exact version installs and
  loads on its own. Pinned, so everyone on a given catalogue release gets the
  same set.
- **stable** — everything _latest_ asserts, plus: **this whole set has a single
  common dependency solution** and every library in it loads. Advances when
  Haywire cuts a release, and may be a smaller set than `latest` — a library
  that cannot be fitted alongside the others is simply not in it.

## What being in this catalogue means — and does not

Merging a library into this repo asserts exactly three things:

1. The distribution exists on PyPI and its wheel contains a valid
   `haybale.toml`.
2. **This name maps to this distribution** — the row you see is generated by
   unzipping the wheel it points at, so it cannot describe one package and
   install another.
3. For the `stable` channel only: this version resolves alongside every other
   library in the set, and imports cleanly.

It asserts **nothing** about whether the code is _safe_, _correct_, _maintained_, or
_fit_ for your purpose. Nobody reads the source. Being listed here is **not a
security review**, and you should evaluate a library exactly as you would any
package you install from PyPI.

## Getting your library listed

### Requirements

- **Published on PyPI.** Git-installable libraries are not accepted, from
  anyone, including us. A PyPI version is immutable — it can be deleted or
  yanked, but never replaced with different content.
- **A valid `haybale.toml` inside the wheel**, with at minimum `name` and
  `version`.
- **A `haywire.libraries` entry point** declared in your `pyproject.toml`.
- **A name not already claimed** by another catalogue entry or by the
  framework's own feed.

Publishing to PyPI is your own step — `haywire share` does not do it. Check [publish-to-pypi]([Publishing to PyPI - Haywire Documentation](https://going-haywire.github.io/haywire/docs/guides/publish-to-pypi/)) for more information. 

Once you are on PyPI, declare it so your own feed advertises the same coordinate this catalogue will:

```toml
# pyproject.toml, at your project root
[tool.haywire.marketstall]
distribute = "pypi"
```

Without that, your own `marketstall.toml` advertises a git coordinate while
this catalogue advertises a pip one, and anyone subscribed to both sees your
library twice, in conflict.

### Submitting

Open an issue using the **Add a library** template. Fill in the distribution
name, the source repository, and a contact.

A bot reads the issue, writes the registry entry, runs the checks, and opens a
pull request that closes your issue. The verdict is posted back on your issue,
so if something fails you find out there rather than having to go looking.

A curator reviews and merges. After that:

- your library appears in **edge** on the next nightly run;
- it appears in **latest** at the next catalogue release, if it loads cleanly;
- it appears in **stable** at the next Haywire release, if it can be fitted
  alongside everything else.

Nobody promotes anything between channels. Placement is computed from the
checks, every time.

### Updating

Nothing to do. Publish to PyPI as usual. `edge` picks up your release the next
night; the pinned channels pick it up at their own cadence.

### Removal

Ask, in an issue, and we remove the registry entry. Existing installations keep
working — removal takes the library out of the catalogue, it does not uninstall
anything. Subscribers see the row marked stale on their next refresh.

## Why isn't my newest version in `stable`?

Readn[stable-report.md](https://going-haywire.github.io/marketplace/stable-report.md). It lists every library in the catalogue with its newest release, the version `stable` currently pins, and — when those differ — which of four reasons
applies:

| reason               | meaning                                                                                                         | what to do                                                             |
| -------------------- | --------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| `conflict`           | your version's dependencies cannot be satisfied alongside the rest of the set. The report names the exact clash | widen the constraint if you can, or wait for the other library to move |
| `failed-load`        | it installed, then failed to import. The report carries the error                                               | fix and release                                                        |
| `held`               | a curator deliberately pinned the set below your version. The report says why                                   | read the reason; open an issue if you disagree                         |
| `not-yet-considered` | you released after the last catalogue run                                                                       | nothing — the next run will pick it up                                 |

The report is regenerated with every solve, so it is never stale, and it is
produced by the same command that produces the lock — it cannot describe a
different set than the one that shipped.

## How `stable` is chosen

Not by hand-picking versions and testing them. The set is **derived by a
resolver**, and this is the whole process:

### Inputs

```text
the library names in registry/*.toml
+ haywire-core, haywire-studio, nicegui  pinned to the target Haywire release
+ stable.constraints.txt                 the curator's holds and exclusions
+ --universal                            resolve across all platforms at once
+ --exclude-newer <timestamp>            freeze the view of PyPI
```

### The solve

`scripts/solve_stable.py` runs to completion on its own. It asks nothing, picks
no versions by hand, and produces the same answer every time for the same
inputs.

It works by giving the resolver an objective it does not have on its own. Every
library gets two bounds:

- a **hard floor** at its current stable pin, so the set can never go backwards;
- an **aspiration** at its newest release.

It resolves. If everything fits, that is the answer and the run is over. If it
does not, the resolver's error names the libraries in the clash — and the solve
relaxes exactly one of their aspirations back to its hard floor, records why,
and resolves again. Two or three passes settle it; each pass is one resolver
call, and only the libraries the resolver actually named are ever candidates.

**Which one gets relaxed** is decided in this order:

1. Whichever relaxation leaves **the most libraries at their newest version**.
2. On a tie, the **more recently released** one. The rest of the set was
   working; the new release is what broke the fit, and its author is the person
   who can widen a constraint. It is also self-correcting — next cycle it is no
   longer the newest.
3. Unless `stable.constraints.txt` says otherwise, which always wins.

Every relaxation lands in `stable-report.md` with the resolver's own
explanation and what taking the newer version would have cost.

### Overriding the outcome

The solve is local. Add a line to `stable.constraints.txt` — `haybale-visiongraph<2.0`, say — re-run, and read the diff of `locks/stable.toml`: every library whose version moved as a consequence. That diff is the answer to "what does holding this back cost us". Discard it and try something else; nothing is pushed until it is right.

You should not normally need to. In an ordinary cycle the solve runs, the lock
diff is the answer, and the constraints file is untouched.

### Verification

The chosen lock and the constraints change go into one pull request. CI then:

- **recompiles from scratch** and fails if the committed lock is not what those
  inputs produce — which is why the resolution is timestamp-frozen, so CI and
  the curator see the same PyPI;
- **installs and imports** every pinned version, in a job with no permissions
  and no secrets;
- **checks PyPI for yanked releases**, because an exact `==` pin installs a
  yanked version anyway. Yanking is the one safety signal our own pinning
  defeats, so it is checked explicitly.

Only then is the lock merged, tagged, and deployed.

## Repo layout

```text
registry/<dist-name>.toml   one file per catalogue member. Human-edited.
stable.constraints.txt      curator holds and exclusions, each with a reason
locks/stable.toml           the solved set, plus the Haywire release it was solved against
locks/latest.toml           the newest-at-release-time set
scripts/                    generator, solver, verifier
```

Everything under `https://going-haywire.github.io/marketplace/` is generated.
Do not edit it; edit the inputs and re-run.

## For curators

The release ritual, in order:

1. The scheduled job opens an issue listing libraries with releases newer than
   the current lock. That is the trigger.
2. Run `scripts/solve_stable.py`. It completes on its own — read the lock diff
   and the report. Only if you disagree with a relaxation does
   `stable.constraints.txt` come into it.
3. Open a PR with the constraints change, the lock, and the report. CI verifies.
4. Merge, tag, deploy.

`CODEOWNERS` puts `registry/`, `stable.constraints.txt` and `locks/` under
`@going-haywire/curators`. Membership is the only judgement call in the system;
everything downstream of it is computed, so keep it that way — do not
hand-edit a lock or a generated feed to work around a failing check.
