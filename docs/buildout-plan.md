# Build the `going-haywire/marketplace` repo — standalone handoff plan

**This plan is self-contained.** It assumes no access to the `going-haywire/haywire`
working tree and no prior conversation. Everything needed to build the repo
correctly is written out below, including the format specs and the constraints
that are silently catastrophic to get wrong.

Companion documents in the haywire repo, for background only — the plan does
not depend on them: `docs/haybale/marketplace/curated-marketplace.md` (design
rationale) and `docs/superpowers/plans/2026-08-27-curated-marketplace-README.md`
(the README to ship, verbatim).

---

## 1. What you are building

Haywire is a visual programming system. Its plugin libraries are called
**haybales**, distributed as ordinary Python packages and discovered through
**feeds** — TOML files a studio subscribes to by URL.

Two feeds exist in this ecosystem:

- The **Official feed**, published by the `going-haywire/haywire` monorepo at
  `https://going-haywire.github.io/haywire/marketplace.toml`. It carries the
  framework's own libraries, which are version-locked to the framework. **Not
  your concern.**
- The **curated marketplace** — what you are building. It carries
  `going-haywire`-owned standalone libraries and selected third-party ones, in
  three channels.

You are building a repo that holds a **list** of libraries plus the tooling
that turns that list into three published TOML feeds. It hosts no packages;
PyPI serves every artifact.

### The three channels

| channel | `install_spec` | asserts | regenerated |
| --- | --- | --- | --- |
| `edge` | unpinned (`haybale-foo`) | membership + identity | nightly |
| `latest` | `haybale-foo==<newest at tag time>` | + installs and **loads** on its own | at each curation tag |
| `stable` | `haybale-foo==<solved>` | + the whole set **resolves and loads together** | at each haywire release |

`edge` is regenerated nightly *despite* its spec floating, because the studio
computes "update available" as `installed_version < row.version`. A frozen
`version` field would mean edge subscribers are never offered an update.

## 2. Five constraints that must not be broken

These are inlined rather than cited because each fails silently or expensively.

### 2.1 The permission split is the security boundary

Installing a wheel executes nothing. **Importing it does.** Two workflow tiers,
and the tier that can write must never run submitted code:

| tier | permissions | may do |
| --- | --- | --- |
| privileged | `contents: write`, deploys Pages | unzip wheels, read metadata, resolve dependencies, generate files, deploy |
| untrusted | `permissions: {}`, no secrets, `pull_request` trigger | `pip install` **and import** candidate libraries |

Row generation never needs execution — reading a library's metadata out of a
wheel is unzipping. So the writing tier has no reason to import anything, and
the importing tier has nothing to steal. Getting this wrong turns a curated
marketplace into a supply-chain vector aimed at its own subscribers.

### 2.2 Every field in a row comes from the artifact

A row is generated by downloading the wheel being pinned, unzipping it, and
reading the `haybale.toml` inside. **The curator authors no field** — not even
an advisory `deprecated` note. A library to be dropped is removed from the
registry, never annotated.

This exists to make one attack impossible: if rows merely *linked* to a file in
the author's repo, an author could keep `name = "haybale-foo"` and repoint
`install_spec` at a different distribution, and every subscriber would follow
on their next refresh. Reading metadata out of the wheel makes the row and the
payload the same object.

### 2.3 The relaxation rule for `stable`

A dependency resolver optimises nothing. It returns *a* solution, preferring
high versions in its own traversal order, so left alone it will silently hold
one library three releases back to let an obscure one be current.

Supply the objective it lacks, as floors:

```text
hard floor,  every library:  >= its current stable pin      # stable never regresses
aspiration,  every library:  >= its newest release

loop:
    resolve(hard floors + aspirations)
    success → done
    failure → the resolver's derivation names the conflicting libraries.
              relax ONE named aspiration to its hard floor, record why, loop.
```

Which named library gets relaxed, in order:

1. Whichever relaxation leaves **the most libraries at their newest**.
2. On a tie, the **more recently released** one — the rest of the set was
   working; the new release broke the fit, and its author can widen a
   constraint. Self-correcting: next cycle it is no longer newest.
3. `stable.constraints.txt` overrides both.

**Only libraries the resolver actually named are relaxation candidates.** Parse
them out of uv's derivation output. Falling back to "try every library" turns a
two-call loop into an N-call one.

**Never test libraries one at a time against a frozen baseline.** If
`haybale-a 2.0` and `haybale-b 2.0` both need `numpy>=2` while the current pins
hold both below it, A alone fails and B alone fails — and you would report both
as conflicted when moving **both together** resolves cleanly. Libraries that
must advance together are invisible to a per-library sweep; the loop above
handles them for free.

### 2.4 `--exclude-newer` or lock verification is unsound

CI recompiles the lock from scratch and fails if the committed lock differs
from what the inputs produce. That check is only sound if the resolution is
time-pinned — otherwise a release appearing between the curator's solve and
CI's makes the two disagree legitimately, and the build fails for no reason.

Pass `uv pip compile --exclude-newer <timestamp>`, write the timestamp into the
lock header, and have CI read it back and reuse it verbatim.

### 2.5 Yanking does not protect a pin

Under [PEP 592](https://peps.python.org/pep-0592/), a yanked release is ignored
by resolvers **unless the requirement pins that exact version with `==`** —
which every `stable` and `latest` row does. An author's "do not use this
release" signal is precisely the one our pinning defeats.

Query `https://pypi.org/pypi/<name>/json` for `yanked` on every pinned version
before deploying, and fail the lock when one is yanked.

## 3. The file formats you must emit

### 3.1 A channel feed

One file per channel, with rows **inline**. Do not use the two-tier
`[[stalls]]`-plus-subdirectory layout: a subscribing studio fetches the feed and
then fetches every `[[stalls]]` URL it lists, so two-tier costs 1 + N HTTP
requests per refresh where inline costs one.

```toml
# https://going-haywire.github.io/marketplace/stable/marketplace.toml

[[haybales]]
name              = "haybale-visiongraph"
label             = "Visiongraph"
version           = "0.0.36"
require           = "haywire-core>=0.1.0"
description       = "Computer-vision pipeline library…"
source            = "pypi"
install_spec      = "haybale-visiongraph==0.0.36"
tags              = ["computer vision", "camera"]
os                = ["macos", "linux"]
on_reload         = "restart"
linked_libraries  = ["haybale_core"]
origin            = "https://github.com/going-haywire/haybale-visiongraph"
origin_provider   = "github"

[[haybales.authors]]
name = "cansik"
url  = "https://github.com/cansik"
```

**Field order**, matching the consumer's own serializer — keep it, so a
generated feed and a studio-written one are shape-compatible:

```text
name, label, version, require, description, source, install_spec, tags, os,
on_reload, linked_libraries, origin, origin_provider, notes, homepage_url,
documentation_url, issues_url, examples_path, tests_path, authors, deprecated
```

Omit empty and default-valued fields.

**Never emit `via`, `last_seen`, or `stale`.** Those three are written by a
*consumer's* refresh into its own cache. A publisher emitting them is
publishing another machine's state.

**Hard requirements enforced by the consumer's parser** — violate either and
the whole feed raises `MalformedMarketplaceError`, which the studio surfaces as
an error banner with no automatic recovery:

- `name` must be a non-empty **string**
- `version` must be a non-empty **string**

> **Serialization trap, and it has already bitten this ecosystem once.**
> If you parse TOML with `tomlkit`, its `String` type is a `str` **subclass**.
> Handing those values to `toml.dumps` serializes each one as a *sequence of
> characters* — `version = ["0", ".", "0", ".", "3", "6"]` — which the consumer
> parser rejects. Normalise every value with `str(...)` before writing, or
> parse with `tomllib` and never let a tomlkit type reach the writer. A
> published first-party feed shipped broken this way and nobody noticed,
> because the corrupted file parsed fine as TOML.

### 3.2 `version` vs `install_spec`

They must agree. `version` drives the studio's update indicator
(`installed < version` ⇒ update available); `install_spec` is passed verbatim
to `uv pip install`. A row advertising `version = "1.4.0"` with a bare
`install_spec = "haybale-foo"` shows a phantom update forever, because clicking
it installs whatever PyPI currently serves and the comparison never settles.

- `stable` / `latest`: `install_spec = f"{name}=={version}"`
- `edge`: `install_spec = name`, with `version` refreshed nightly so the
  comparison stays meaningful

### 3.3 `require`

The PEP 508 token naming the framework floor, e.g. `"haywire-core>=0.1.0"`.
Copy it from the wheel's declared `haywire-core` dependency. An absent key means
undeclared; the bare name `"haywire-core"` means declared with no floor — those
are different answers, which is why the field carries the package name and not
a bare specifier. The studio checks it as an advisory pre-install gate.

## 4. Repo layout

```text
registry/<dist-name>.toml     membership — human-edited, one file per library
stable.constraints.txt        curator holds and exclusions, each with a # reason
locks/stable.toml             the solved set + the framework versions it was solved against
locks/latest.toml             the newest-at-tag-time set
scripts/
  generate_feed.py            registry + lock  → the published TOML/HTML
  solve_stable.py             the relaxation loop → locks/stable.toml + stable-report.md
  verify_lock.py              recompile, compare, check yanks
docs/design.md                (optional) a copy of the rationale for contributors
.github/
  ISSUE_TEMPLATE/add-library.yml
  workflows/{verify,lock-check,deploy,nightly}.yml
CODEOWNERS
README.md
```

One file per library, not one registry file: submission PRs never conflict,
removal is `git rm`, and per-library history is clean.

A registry entry is small, because everything descriptive comes from the wheel:

```toml
# registry/haybale-visiongraph.toml
name         = "haybale-visiongraph"   # the PyPI distribution name
repo         = "https://github.com/going-haywire/haybale-visiongraph"
contact      = "maybites"
added        = "2026-08-28"
```

## 5. Build order

### 5a. Scaffold

A `uv` project depending on a **published** `haywire-core` — the generator
reuses its row dataclass and strict metadata reader so the emitted shape cannot
drift from what studios parse.

Manual GitHub steps a plan cannot do for you, all needed before 5i:

- create `going-haywire/marketplace`
- create the `@going-haywire/curators` team
- `CODEOWNERS`: that team owns `registry/`, `stable.constraints.txt`, `locks/`
- branch protection on the default branch: require PR review + the `verify` and
  `lock-check` checks
- enable GitHub Pages, source = `gh-pages` branch, root

### 5b. First registry entry, and a fixture

Use `haybale-visiongraph`. Verified on 2026-08-28 and safe to build against:

```text
haybale-visiongraph 0.0.36 on PyPI, not yanked
wheel: haybale_visiongraph-0.0.36-py3-none-any.whl
  haybale_visiongraph/haybale.toml            → name, id, label, version,
                                                 on_reload, linked_libraries, description
  *.dist-info/entry_points.txt                → [haywire.libraries]
                                                 visiongraph = haybale_visiongraph:Library
```

Vendor that wheel as a test fixture so the generator's tests never hit the
network.

### 5c. Generator — `scripts/generate_feed.py`

Reads `registry/*.toml` plus a lock, and for each entry: resolve the wheel URL
from the PyPI JSON API, download, unzip, read the `haybale.toml` inside, build
a row, set `source`/`install_spec`/`version` per the channel. Emits:

```text
index.html                                landing page: the three channels, what each asserts
edge/marketplace.toml
latest/marketplace.toml
stable/marketplace.toml
stable/<curation-tag>/marketplace.toml    immutable archive
latest/<curation-tag>/marketplace.toml    immutable archive
archives.html                             the archive index
stable-report.md
```

**`archives.html` is required, not polish.** GitHub Pages serves no directory
listings — `/stable/` returns 404 unless an index exists there, so without it
the archives cannot be found or chosen between. List each archive with its tag,
date, the `haywire-core` version it was solved against, and its library count.

The generator **never imports** a downloaded package.

### 5d. Solver — `scripts/solve_stable.py`

Runs to completion unattended. Wraps
`uv pip compile --universal --exclude-newer <ts>` over: the registry names, the
framework pins, and `stable.constraints.txt`.

Framework pins are **three** packages, not one — the studio's own install path
constrains all three, and `nicegui` is a real source of conflicts:

```text
haywire-core==X
haywire-studio==X
nicegui==Y
```

`--universal` because libraries declare an `os` field and a set that resolves on
Linux may not on Windows; universal resolution proves all platforms in one pass
via environment markers.

Implements the loop and relaxation rule from §2.3. Writes `locks/stable.toml`
with the `--exclude-newer` timestamp in its header, and `stable-report.md`.

### 5e. `stable-report.md`

One row per library: newest available, the version in the lock, and which of
four states explains a gap.

| state | content |
| --- | --- |
| `held` | the constraint line and its `#` reason |
| `conflict` | the aspiration the solve relaxed, with the resolver's derivation and what taking it would have cost — *"taking 1.4.0 would have forced haybale-y and haybale-z back; the clash is numpy (x wants >=2, y wants <2)"* |
| `failed-load` | the import error from the load gate |
| `not-yet-considered` | released after the last curation tag |

This is the document a library author is pointed at when their newest release
did not land in `stable`, so write it for them, not for curators.

### 5f. Workflows

| file | permissions | trigger | does |
| --- | --- | --- | --- |
| `verify.yml` | `{}`, **no secrets** | `pull_request` | `pip install` + **import** each candidate; assert components register |
| `lock-check.yml` | read | `pull_request` | recompile with the lock's own timestamp; fail if the committed lock differs |
| `deploy.yml` | `contents: write` | tag | yank check, generate, deploy to `gh-pages` |
| `nightly.yml` | `contents: write` | schedule | regenerate `edge`; open the "newer releases available" issue |

Re-read §2.1 before writing these. `verify.yml` is the only one that runs
submitted code and it must hold nothing worth stealing.

`nightly.yml`'s issue is purely informational — it makes no decision. It is the
notification that starts a curation cycle.

### 5g. Issue Form + issue-ops

`.github/ISSUE_TEMPLATE/add-library.yml` collecting distribution name, source
repo, and contact. A workflow parses the issue, writes
`registry/<name>.toml`, runs the gates, opens a PR that closes the issue, and
comments the verdict **on the author's issue** so a failure reaches the person
who can fix it.

The gates at submission:

- the distribution resolves on PyPI
- its wheel contains a `haybale.toml` that passes the strict reader
- it declares a `haywire.libraries` entry point
- the name is not already claimed by another registry entry or by the Official
  feed

### 5h. README

Ship
`docs/superpowers/plans/2026-08-27-curated-marketplace-README.md` from the
haywire repo verbatim as `README.md`. If that file is unavailable, it must
still state — and this is not trimmable — that merging a library asserts
exactly three things:

1. the distribution exists on PyPI and its wheel contains a valid haybale;
2. this name maps to this distribution;
3. for `stable` only: this version resolves alongside the set and imports
   cleanly.

and that it asserts **nothing** about whether the code is safe, correct, or
maintained — **nobody reads the source**. Unsaid, "curated by going-haywire"
implies a review this design cannot back.

### 5i. First deploy

Tag, let `deploy.yml` run, then confirm by hand:

```sh
curl -sf https://going-haywire.github.io/marketplace/stable/marketplace.toml
curl -sf https://going-haywire.github.io/marketplace/latest/marketplace.toml
curl -sf https://going-haywire.github.io/marketplace/edge/marketplace.toml
curl -sf https://going-haywire.github.io/marketplace/archives.html
```

**Then tell the haywire repo.** Its Stage 4 — changing the studio's default
subscriptions to include `stable` — is deliberately held until these URLs
resolve. Shipping it earlier gives every fresh install a permanently
unavailable source with no cached body to fall back on.

## 6. Acceptance

- [ ] All four URLs above return 200 and parse as TOML.
- [ ] Feeding `stable/marketplace.toml` to `haywire.core.marketstall.parsing`
      yields rows with `type(row.name) is str` and `type(row.version) is str` —
      assert on `type(...) is str`, not `isinstance`, or the tomlkit trap
      passes the test and still ships broken.
- [ ] `install_spec` equals `f"{name}=={version}"` for every `stable` and
      `latest` row; equals `name` for every `edge` row.
- [ ] No row carries `via`, `last_seen`, or `stale`.
- [ ] `verify.yml` has `permissions: {}` and no `secrets` reference.
- [ ] `deploy.yml` contains no step that imports a downloaded package.
- [ ] Deleting a `registry/*.toml` and regenerating removes that row from all
      three channels.
- [ ] `lock-check.yml` fails when `locks/stable.toml` is hand-edited.
- [ ] `stable-report.md` explains every library whose lock version is below its
      newest.

## 7. Do not

- Do not add a field to a row that did not come from the wheel.
- Do not import a submitted package in any job that has write permissions.
- Do not use the two-tier `[[stalls]]` layout for a channel.
- Do not hand-edit a lock or a generated feed to get past a failing check.
- Do not have the curated feed subscribe to another feed: a subscribing
  studio resolves only one level deep and ignores a feed's own `[[markets]]`
  entries entirely, so such a link is silently dropped.
